Auditoria técnica & hardening

Blindagem do BFF Sebratel

Auditoria completa do serviço bff-java-service, correção das falhas de menor risco, esteira de segurança no CI e instrumentação de observabilidade — sem nenhuma mudança arquitetural.

  • Repositório dev_SpringBoot_APIGateway
  • Branch staging
  • Stack Java 21 · Spring Boot 3.4.3
  • Data agosto/2026

O ponto de partida

A primeira descoberta foi de nomenclatura, e mudou o foco de todo o trabalho.

O repositório se chama APIGateway, mas o serviço não é um gateway. É um BFF: 50 endpoints REST próprios que consultam bancos diretamente e chamam a API do ERP Elleven. Não há roteamento dinâmico nem repasse de requisição bruta.

Isso elimina por construção uma classe inteira de riscos que normalmente domina a auditoria de um gateway — request smuggling, host header injection, confiança em X-Forwarded-*. Auditadas as 14 chamadas de saída, todas usam host literal: não há SSRF. As ~25 queries nativas usam parâmetros nomeados: não há SQL injection.

Os riscos reais estavam em outro lugar — e eram mais graves.

O que a auditoria encontrou

17 achados de segurança e 5 de dependências. Nada foi classificado como crítico só por parecer suspeito — a severidade reflete o caminho de exploração real neste código.

F-01 Critical Chave privada RSA versionada no Git e embarcada no JAR Exige rotação
F-02 Critical HTTP Basic com credencial estática anula a restrição de domínio do JWT Instrumentado
F-03 High JWT sem validação de audience — token de qualquer app Google é aceito Aguarda client IDs
F-04 High /api/v1/matrix público — oráculo de CPF sem autenticação Instrumentado

F-14 Medium Retry após 401 reenviava exatamente o token que acabara de ser recusado Corrigido

Critério aplicado: severidade mede o risco neste código, não a nota CVSS isolada. Uma CVE crítica em biblioteca que nunca é invocada não vira Critical — vira High com a observação de que não há caminho de execução até ela.

As camadas de defesa

Seis camadas, da mais interna à mais externa. Cada uma pega o que a anterior deixou passar.

Correções no código

camada 1 · runtime

Só mudanças pequenas, localizadas e de baixo risco. Nenhuma refatoração, nenhuma troca de biblioteca, nenhuma alteração de contrato de API.

  • Token bearer removido dos logs — pré-requisito para ligar o APM com segurança
  • joinPoint.proceed(args) no retry: a nova tentativa passa a levar o token renovado
  • Selenium e WebDriverManager removidos — junto foram ~25 artefatos transitivos
  • Datasource morto removido, com IP interno que estava fixo no código

Testes

camada 2 · regressão

Os 25 testes de controller existentes rodavam com addFilters = false: a cadeia de segurança nunca era exercitada. Dava para introduzir um permitAll() acidental com a suíte inteira verde.

A correção foi aditiva — nenhum teste existente foi tocado.

  • SecurityIntegrationTest: 11 cenários com os filtros ligados
  • Sem credencial, senha errada, usuário inexistente e token malformado devem dar 401
  • Rotas públicas conhecidas ficam registradas — quando forem fechadas, o teste falha de propósito
  • TokenRetryAspectTest: prova que o retry leva o token novo

Integração contínua

camada 3 · build

A branch main, que é a de produção, não tinha nenhuma verificação automatizada: os três workflows existentes cobriam só a staging.

  • Build e testes em push e pull request, agora para main e staging
  • clean verify obrigatório — sem ele, classes de builds antigos sobrevivem e quebram a suíte
  • Resumo de testes e cobertura JaCoCo publicados no próprio PR
  • Build da imagem Docker e scan com Trivy

Portões de segurança

camada 4 · bloqueio

Quatro verificações independentes e um portão que agrega o resultado das quatro. O que bloqueia está definido de forma explícita, e o que não bloqueia continua sendo registrado.

  • Segredos novos no diff do PR — bloqueia
  • Dependência com CVSS ≥ 7 — bloqueia
  • Achado de SAST com severidade ERROR — bloqueia
  • Falha nos testes de autenticação e autorização — bloqueia

Os robôs

camada 5 · vigilância contínua

Ferramentas que trabalham sozinhas, inclusive quando ninguém abre PR. A varredura de dependências roda semanalmente por agendamento, porque CVE nova aparece em código que não mudou.

  • Dependabot — alerta e propõe correção para dependências vulneráveis
  • Gitleaks — segredos no diff e no histórico, com valores sempre mascarados
  • Semgrep — SAST com regras públicas mais seis regras escritas para os achados desta auditoria
  • OWASP Dependency-Check — CVEs em dependências diretas e transitivas
  • Trivy — CVEs de sistema operacional na imagem Docker

Observabilidade

camada 6 · produção

Elastic APM Java Agent 1.56.0, falando com o apm-server pela rede Docker interna. A rede foi declarada no repositório, e não criada à mão no Portainer, porque o ambiente é GitOps.

  • Corpo de requisição não é capturado — contém CPF, cookie de sessão e dados de funcionário
  • Captura de headers desligada explicitamente: o padrão do agente é ligado e enviaria Authorization
  • Lista de campos sanitizados estendida com cookiestring, syndata, cpf
  • Nenhuma instrumentação foi desativada — sem evidência de problema, desligar seria injustificado

O que explicitamente não bloqueia

Um portão que bloqueia em tudo é desligado na primeira semana. Achados de severidade baixa, CVEs de sistema operacional da imagem base e supressões com justificativa registrada passam — mas nenhum deles é descartado: todos ficam nos artefatos do run.

Toda supressão exige finding rastreado, justificativa técnica e data de revisão. Não existe mecanismo para silenciar achado inconveniente.

O caso WebDriverManager

Um exemplo concreto de duas camadas independentes chegando à mesma conclusão.

Como uma dependência esquecida virou risco crítico

  1. A auditoria manual notou que selenium-java e webdrivermanager estavam no build sem nenhuma referência no código — nem em src/main, nem em src/test.
  2. Foram removidos. Junto saíram ~25 artefatos transitivos, incluindo o BouncyCastle 1.76 e um bloco do OpenTelemetry que poderia conflitar com o agente do APM.
  3. Dias depois, o Dependabot abriu um alerta independente na mesma dependência: XXE, CVSS 9.3 Critical. Uma CVE direta que a análise manual de versões não tinha identificado.
  4. O Dependabot propôs atualizar para a versão 6.1.0. Essa era a correção errada — a dependência não é usada por nada. Atualizar manteria os 25 artefatos e apenas moveria a superfície de ataque de lugar.

A lição para o processo: a análise manual acertou o diagnóstico e a remediação, mas errou a severidade — e foi o robô que corrigiu. É exatamente por isso que a auditoria registra que o scanner, e não a análise humana de versões, é a fonte autoritativa sobre CVEs.

O que ainda está aberto

O trabalho não termina porque o build ficou verde. Estes pontos dependem de decisão ou de medição — nenhum deles deve ser fechado no escuro.

Pendência Por que ainda não foi feita O que destrava
Rotação da chave RSA F-01 QR Codes já emitidos deixam de ser decifráveis com a chave nova Definição de janela de transição pelo negócio
Fechar o HTTP Basic F-02 Remover às cegas derrubaria integrações desconhecidas Dados do filtro de auditoria, já coletando em produção
Validar o audience do JWT F-03 Se web e mobile usam client IDs diferentes, validar um só derruba um deles Levantamento dos client IDs legítimos
Timeout no cliente HTTP F-15 O valor certo vem da latência real, não de um palpite Uma semana de dados do APM
Modelo de autorização F-09 Mudança arquitetural — hoje qualquer autenticado acessa tudo Definição de papéis pelo negócio
Rate limiting F-10 Pertence ao proxy reverso, que está fora deste repositório Configuração no Traefik/nginx

O filtro de auditoria é temporário e tem função única: registrar, a cada requisição, qual mecanismo de autenticação foi usado e de onde vieram as chamadas anônimas. Ele não altera requisição, resposta nem contexto de segurança, e engole qualquer erro interno para nunca derrubar uma chamada real. Sai de cena assim que F-02 e F-04 forem fechados.

Princípios que guiaram o trabalho

  • Preservar o comportamento atual sempre que não houvesse motivo de segurança para mudá-lo
  • Nenhuma refatoração massiva, troca de framework ou alteração de contrato de API
  • Medir antes de otimizar — nenhuma mudança de performance especulativa foi aplicada
  • Instrumentar antes de endurecer, quando fechar uma porta poderia quebrar um consumidor desconhecido
  • Toda correção de segurança acompanhada de teste, quando tecnicamente possível
  • Nenhum achado silenciado: o que não bloqueia continua registrado e rastreável
